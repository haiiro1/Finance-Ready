# HU-0111 - Implementar el modelo visual del microfrontend Bancos y tarjetas

## Objetivo

Adaptar el contenido principal de `preview (2).html` al apartado `/bancos-tarjetas`, reutilizando el shell autenticado definido en HU-0109 y los colores establecidos en `docs/DesignSystem-V1.md`.

Esta HU debe incorporar solamente el contenido propio del dominio Bancos y tarjetas. No debe copiar ni volver a implementar:

- Sidebar.
- Header o topbar.
- Busqueda global.
- Notificaciones.
- Perfil del usuario.
- Cambio de tema global.
- Cierre de sesion.

Esos elementos pertenecen al shell y deben envolver el microfrontend mediante el `Outlet` o mecanismo de composicion vigente.

## Historia de usuario

Como usuario autenticado
quiero visualizar el espacio de bancos y tarjetas con una estructura clara para productos, cupos, ciclos y fechas de pago
para comprender el alcance del modulo y preparar su futura integracion con datos financieros reales.

## Decision de arquitectura

El repositorio contiene `frontend/apps/bancos-tarjetas/package.json`, pero el paquete puede continuar sin scaffold o composicion real con el shell.

Antes de implementar:

- Si ya existe un mecanismo de composicion, el contenido debe vivir en `frontend/apps/bancos-tarjetas/` y exportarse mediante ese contrato.
- Si no existe, la vista debe vivir temporalmente en `frontend/apps/shell/src/bancos-tarjetas/` y conectarse a `/bancos-tarjetas` desde el shell.
- No se debe inventar Module Federation, iframes, un segundo router o un segundo `ThemeProvider`.
- La ubicacion temporal debe quedar documentada como deuda arquitectonica.
- El dominio no debe importar componentes internos de Dashboard o Finanzas.

## Nota obligatoria sobre Tailwind y temas

No repetir el problema detectado durante HU-0110.

La configuracion Tailwind 4 y los tokens globales son responsabilidad del shell:

```text
frontend/apps/shell/src/index.css
frontend/apps/shell/tailwind.config.js
```

Antes de crear estilos, verificar que `index.css` ya contenga y conserve:

```css
@import 'tailwindcss';
@config '../tailwind.config.js';
@source '../../../packages/ui-kit/src';
@variant dark (&:where(.dark, .dark *));
```

Reglas:

- No duplicar `@config`, `@source`, `@variant`, variables `:root` o `.dark` dentro del microfrontend.
- No crear otro archivo global con una segunda paleta.
- No copiar las variables CSS hardcoded del mockup.
- Usar utilidades semanticas existentes: `bg-background`, `bg-card`, `bg-popover`, `text-foreground`, `text-muted-foreground`, `border-border`, `border-input`, `bg-primary`.
- Si una utilidad semantica no genera CSS, revisar primero la carga de `tailwind.config.js`; no reemplazarla inmediatamente por colores hardcoded.
- No añadir un segundo `ThemeProvider` ni manipular `data-theme` manualmente.
- Para `<select>` nativos, validar el control cerrado y el listado de `<option>` abierto en claro y oscuro.
- Modales y popovers deben usar superficies opacas `bg-popover` o `bg-card`; el overlay no debe reducir la opacidad del contenido.
- Cualquier cambio en `index.css` afecta todo el shell y debe validarse también en autenticacion, dashboard y finanzas.

## Decision de alcance

### Incluye

- Contenido visual del modulo Bancos y tarjetas.
- Tabs y paneles locales del dominio.
- Metricas, productos, ciclos, alertas y estados vacios.
- Preview no persistente del formulario de banco o tarjeta, si cumple accesibilidad y claridad.
- Componentes presentacionales y tipos locales del dominio.
- Fixtures tipados cuando sean necesarios para reproducir el modelo visual.
- Uso de componentes genericos existentes en `@finance-ready/ui-kit`.

### No incluye

- Sidebar o header propios.
- Registro, edicion o eliminacion real de bancos y tarjetas.
- Sincronizacion, importacion o conexion bancaria.
- Pagos reales o programacion de pagos.
- Calculo real de saldo, cupo, uso, pago minimo o pago recomendado.
- Integracion backend.
- Nuevas rutas `/bancos` o `/tarjetas`.
- Persistencia de tabs en URL si no existe una decision de navegacion previa.
- Librerias externas de charts, tabs, iconos o formularios.

## Modelo visual esperado

### Encabezado del dominio

Elementos:

```text
Proximo modulo
Bancos y tarjetas
Gestion de bancos, tarjetas, cupos, ciclos y fechas de pago.
```

Acciones previstas:

```text
Agregar banco
Agregar tarjeta
Crear producto
```

Mientras no exista persistencia:

- No confirmar que un producto fue creado.
- No mostrar toast de exito falso.
- Mantener las acciones disabled, marcadas como `Proximamente` o abrir un preview que indique que no guarda.

### Tabs

Tabs previstas:

```text
Resumen
Bancos
Tarjetas
Estado inicial
```

Reglas:

- Implementar con estado React, no con `document.querySelectorAll`.
- Usar semantica accesible de tabs o botones con estados `aria-selected` y panel asociado.
- Preservar foco visible y navegacion por teclado.
- La tab activa usa acento teal suave, no colores hardcoded del mockup.

### Metricas del resumen

Metricas previstas:

```text
Saldo disponible
Cupo utilizado
Proximo pago
Productos activos
```

Reglas:

- Cuatro columnas en desktop, dos en tablet y una en mobile.
- Sin fuente real, mostrar `Sin datos` o identificar toda la seccion como demo.
- No usar `$0` como valor calculado confirmado.
- Cada monto debe incluir codigo de moneda, por ejemplo `CLP`.
- Un porcentaje debe indicar su denominador: cupo usado respecto del cupo total.
- `Proximo pago` debe distinguir fecha de vencimiento, monto facturado, pago minimo y pago recomendado.

### Productos financieros

Cada item debe reservar espacio para:

- Institucion.
- Tipo de producto.
- Moneda.
- Saldo disponible, deuda o cupo, con etiqueta explicita.
- Fecha de ultima actualizacion cuando exista.
- Barra de uso con descripcion textual.
- Acciones futuras claramente no disponibles.

No usar una unica etiqueta `Disponible` para cuentas y tarjetas si representa magnitudes distintas.

Para tarjetas se debe diferenciar:

```text
Cupo total
Cupo utilizado
Cupo disponible
Monto facturado
Pago minimo
Pago recomendado
Fecha de cierre
Fecha de vencimiento
```

### Proximos ciclos

Preparar filas para:

- Producto.
- Tipo de evento: cierre o vencimiento.
- Fecha.
- Estado.
- Monto aplicable y moneda.

Reglas financieras:

- `Cierre` no equivale a `Vencimiento`.
- `Pendiente` no equivale a `Atrasado`.
- El pago minimo no debe presentarse como pago recomendado.
- No usar danger para un pago futuro solo porque sea una deuda.

### Alertas

Alertas previstas:

- Uso de cupo elevado.
- Producto sin movimientos recientes.
- Proximidad de cierre o vencimiento.

Sin reglas reales, mostrar ejemplos solo dentro de una vista demo identificada. No derivar alertas con porcentajes arbitrarios en produccion.

### Vista Bancos

- Lista de instituciones registradas.
- Cantidad de productos asociados.
- Ultima actualizacion.
- Saldo agregado con moneda explicita solo cuando exista calculo confiable.
- Estado vacio para agregar la primera o una nueva institucion.

No sumar saldos de monedas diferentes.

### Vista Tarjetas

- Lista de tarjetas.
- Cupo total, utilizado y disponible.
- Ciclo de facturacion y vencimiento.
- Estado vacio si no existen tarjetas.
- Accion `Ver cuotas` deshabilitada o proxima mientras no exista flujo.

### Estado inicial

Copy recomendado:

```text
Configura tu primer banco o tarjeta
Cuando agregues productos, podras revisar saldos, cupos, ciclos y proximos pagos desde este modulo.
```

Acciones:

- Volver a `/dashboard` puede ser funcional.
- `Agregar banco` debe respetar la condicion no persistente de esta HU.

### Modal de banco o tarjeta

El mockup contiene un modal con institucion, tipo y saldo o cupo inicial. Se permite implementarlo solo como preview.

Condiciones:

- Titulo dinamico claro: `Agregar banco` o `Agregar tarjeta`.
- Debe anunciar que no guarda informacion.
- No ejecutar `saveModal`, mostrar exito ni agregar productos a la lista.
- Cierre por boton, backdrop cuando corresponda y tecla `Escape`.
- Gestionar foco inicial y devolverlo al trigger al cerrar.
- Labels visibles y controles asociados.
- Superficie opaca `bg-popover` o `bg-card`.
- Inputs, select y options legibles en ambos temas.
- El campo monetario no debe convertirse a `float`.
- Moneda explicita y separada del valor cuando llegue la implementacion funcional.
- Si el preview no cumple estas condiciones, usar acciones disabled con texto `Proximamente`.

## Datos demo y contratos visuales

Si son necesarios fixtures para validar la composicion:

- Centralizarlos en un archivo como `bankingDemoData.ts`.
- Usar tipos explicitos; no usar `any`.
- Marcar los datos como demo en codigo e interfaz.
- No copiar nombres, email, instituciones, tarjetas o montos personales del mockup.
- Incluir moneda en cada importe.
- No usar `float` para representar dinero.
- Mantener fechas de cierre y vencimiento como campos distintos.
- Mantener estados `pending`, `paid` y `overdue` mutuamente coherentes.
- Facilitar el reemplazo posterior por contratos de `@finance-ready/shared-types`.

## Reglas de color y estilo

Usar `docs/DesignSystem-V1.md`:

- Fondo: `background`.
- Cards: `card`.
- Modal y dropdown: `popover`.
- Texto principal: `foreground`.
- Texto secundario: `muted-foreground`.
- Accion primaria y tab activa: teal.
- Saldo o estado favorable verificable: success/emerald.
- Uso elevado o proximidad de vencimiento: warning/amber.
- Atraso, error o riesgo critico: danger/rose.
- Superficies deshabilitadas: muted/slate.
- Bordes y radios moderados.
- Sombras minimas.
- Sin glassmorphism, gradientes decorativos o colores neon.

El mockup usa colores y variables propios. Deben traducirse a los tokens reales, no copiarse literalmente.

## Riesgo residual

- `frontend/apps/bancos-tarjetas/` puede continuar sin scaffold ni composicion real con el shell.
