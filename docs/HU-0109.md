# HU-0109 - Implementar el modelo visual del dashboard

## Objetivo

Adaptar el mockup interactivo `finance-ready-dashboard-mockup-interactivo.html` a la arquitectura React real de Finance Ready y convertirlo en el modelo visual de referencia para el shell autenticado y la ruta `/dashboard`.

El resultado debe conservar la composicion, densidad y jerarquia del mockup:

- Sidebar agrupado por dominios.
- Header superior con busqueda, notificaciones, tema y perfil.
- Encabezado contextual con saludo y acciones rapidas.
- Cuatro metricas financieras principales.
- Panel de proximos vencimientos con linea temporal.
- Panel de bancos y productos.
- Soporte claro, oscuro y responsive.

El HTML entregado es una referencia visual e interactiva, no codigo para copiar directamente. La implementacion debe usar React, TypeScript, Tailwind CSS 4, React Router y el `ui-kit` existente.

## Historia de usuario

Como usuario autenticado
quiero ver un dashboard financiero organizado y escaneable
para comprender rapidamente mi disponibilidad mensual, compromisos, deudas, ahorro proyectado y proximos vencimientos.

## Criterios de aceptacion

- [ ] El shell autenticado usa una sidebar de aproximadamente `268px` en desktop y un mecanismo de navegacion accesible en mobile.
- [ ] La sidebar agrupa las rutas bajo `General`, `Cuentas`, `Compromisos` y `Analisis`.
- [ ] La navegacion activa usa fondo teal suave y texto teal, con hover visible en ambos temas.
- [ ] El header es sticky e incluye busqueda, notificaciones, cambio de tema y perfil del usuario.
- [ ] La busqueda deja claro si aun no existe integracion funcional y no devuelve resultados inventados.
- [ ] El dashboard incluye encabezado contextual, descripcion breve y acciones rapidas.
- [ ] Se representan las metricas `Disponible este mes`, `Gastos comprometidos`, `Deudas activas` y `Ahorro proyectado`.
- [ ] El dashboard incluye un panel de proximos vencimientos y una linea temporal horizontal.
- [ ] El dashboard incluye un panel de bancos y productos con uso de cupo o capacidad visualmente legible.
- [ ] Montos, monedas, fechas, porcentajes y estados no se presentan como datos reales si no provienen de una fuente confiable.
- [ ] Los datos de demostracion, si son necesarios para reproducir el modelo visual, quedan centralizados, tipados y marcados explicitamente como demo.
- [ ] Los estados success, warning y danger respetan la semantica de `docs/DesignSystem-V1.md`.
- [ ] El usuario autenticado y su email provienen de `useAuth`; no se hardcodean nombres ni correos personales del mockup.
- [ ] El logo usa los assets existentes de Finance Ready; no se usa el emoji del mockup.
- [ ] El diseño funciona en desktop, tablet y mobile sin ocultar la unica via de navegacion.
- [ ] El diseño funciona en modo claro y oscuro.
- [ ] No se copia `<style>`, `<script>`, handlers inline ni manipulacion directa del DOM desde el mockup.
- [ ] No se agregan dependencias externas para iconos, graficos o layout sin una justificacion separada.
- [ ] `pnpm.cmd lint` y `pnpm.cmd build` pasan.

## Decision de alcance

### Incluye

- Rediseño del `ShellLayout` autenticado.
- Rediseño de `/dashboard` siguiendo el mockup.
- Sidebar con grupos visuales y rutas existentes.
- Header sticky con controles del mockup adaptados a componentes React.
- Cards de metricas, vencimientos, timeline y productos bancarios.
- Estados visuales hover, active, focus, disabled y responsive.
- Reutilizacion o creacion de componentes presentacionales pequeños y tipados.
- Datos demo centralizados solo cuando sean necesarios para validar la composicion antes de integrar backend.

### No incluye

- Implementacion real de busqueda global.
- Centro de notificaciones.
- Creacion real de bancos, ingresos o deudas.
- Consultas backend nuevas.
- Calculo real de saldos, capacidad, gastos, ahorro o porcentajes.
- Graficos financieros.
- Scaffold o federacion del paquete `frontend/apps/dashboard/`.
- Cambios en autenticacion, JWT o contratos financieros.
- Rediseño funcional de los otros microfrontends.

## Reglas de adaptacion del mockup

### Elementos que deben conservarse

- Layout desktop con sidebar fija y contenido flexible.
- Sidebar sobria con marca, grupos, navegacion y sesion al pie.
- Header de `64px` aproximados con busqueda flexible y acciones compactas.
- Contenido con ancho maximo aproximado de `1240px`.
- Hero compacto con saludo, resumen y acciones rapidas.
- Grid de cuatro metricas.
- Layout principal de dos columnas con proporcion aproximada `1.55fr / 0.9fr`.
- Cards con borde sutil, radio moderado y sombra minima.
- Timeline desplazable horizontalmente cuando no exista espacio.
- Paleta slate + teal y estados emerald, amber y rose.

### Elementos que deben adaptarse

- Reemplazar el emoji de marca por `/fr-icon.svg` o el asset oficial vigente.
- Reemplazar simbolos de texto usados como iconos por una solucion accesible existente; no agregar una dependencia solo por decoracion.
- Obtener perfil y email desde `useAuth`.
- Usar `ThemeSwitcher` o la API de tema existente en lugar de modificar `data-theme` manualmente.
- Usar `NavLink` para estados activos, no listeners sobre botones.
- Usar estado React para cualquier feedback temporal; no usar `document.getElementById`.
- No reproducir el email, nombre ni datos financieros personales incluidos en el archivo de referencia.
- No dejar botones que aparenten persistir datos. Las acciones sin flujo real deben estar deshabilitadas o indicar claramente `Proximamente`.

### Ajuste obligatorio para mobile

El mockup oculta completamente la sidebar bajo `900px`. La implementacion real debe proporcionar una alternativa accesible:

- Boton de menu visible en el header.
- Drawer, panel colapsable o navegacion equivalente.
- Cierre por boton, seleccion de ruta y tecla `Escape` cuando corresponda.
- Bloqueo de scroll de fondo si se usa overlay.
- Foco visible y orden de tabulacion correcto.

## Modelo visual esperado

### Sidebar

Orden y agrupacion recomendados:

```text
GENERAL
  Dashboard
  Finanzas

CUENTAS
  Bancos y tarjetas

COMPROMISOS
  Prestamos y deudas
  Suscripciones

ANALISIS
  Reportes
  Configuracion
```

No crear rutas separadas `/bancos` y `/tarjetas` mientras la arquitectura vigente conserve `/bancos-tarjetas`.

Pie de sidebar:

- Estado de sesion.
- Email real del usuario autenticado.
- Cambio de tema si no queda disponible en el header.
- Accion `Cerrar sesion`.

Evitar duplicar el selector de tema en sidebar y header salvo que exista una razon responsive concreta.

### Header

- Altura compacta y posicion sticky.
- Busqueda con label accesible y placeholder `Buscar movimientos, bancos, deudas...`.
- Boton de notificaciones con nombre accesible.
- Selector de tema.
- Perfil con avatar derivado de iniciales seguras y nombre/email disponible.
- En mobile, boton de menu antes de la busqueda o en reemplazo parcial de ella.

Si busqueda y notificaciones no estan implementadas, deben comunicar su estado sin simular resultados.

### Encabezado del dashboard

- Saludo derivado del usuario cuando exista nombre disponible.
- Texto de resumen solo si procede de datos reales; de lo contrario usar copy neutral.
- Acciones rapidas previstas:
  - `Agregar banco`.
  - `Registrar ingreso`.
  - `Crear deuda` como accion primaria.

Mientras sus flujos no existan, estas acciones no deben navegar a rutas falsas ni confirmar operaciones inexistentes.

### Metricas

Cards previstas:

```text
Disponible este mes
Gastos comprometidos
Deudas activas
Ahorro proyectado
```

Reglas:

- Importes con moneda explicita.
- Porcentajes y pills con contexto.
- Success no significa automaticamente dinero positivo; debe expresar un estado favorable verificable.
- Warning identifica compromisos o atencion.
- No mostrar `$0` como si fuera un calculo confirmado cuando la integracion aun no existe.
- Para datos no disponibles, preferir `Sin datos`, `Pendiente de conectar` o skeleton solo durante una carga real.

### Proximos vencimientos

Cada fila debe reservar espacio para:

- Nombre de obligacion.
- Tipo o contexto.
- Fecha de vencimiento.
- Monto y moneda.
- Estado semantico.

La timeline debe ser complementaria y no sustituir la informacion textual. En mobile puede desplazarse horizontalmente sin provocar scroll en toda la pagina.

### Bancos y productos

Cada item debe reservar espacio para:

- Institucion.
- Tipo de producto.
- Saldo, deuda o cupo con etiqueta inequivoca.
- Barra de uso solo cuando numerador, denominador y unidad tengan significado definido.

No usar una barra teal sin explicar si representa saldo, cupo utilizado, capacidad o progreso.

## Datos demo y contratos visuales

Si todavia no existen endpoints para alimentar el dashboard, se permite usar fixtures exclusivamente para construir y revisar la UI.

Condiciones:

- Deben vivir en un archivo identificable, por ejemplo `frontend/apps/shell/src/dashboard/dashboardDemoData.ts`.
- Deben usar tipos explicitos; no usar `any`.
- Deben incluir moneda en importes.
- Deben estar marcados como datos demo en codigo y, durante validacion, en la interfaz.
- No usar nombres, emails, bancos, deudas o montos personales del usuario contenidos en el mockup.
- Debe ser sencillo reemplazarlos por una fuente real sin reescribir componentes visuales.
