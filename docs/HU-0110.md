# HU-0110 - Implementar el modelo visual del microfrontend Finanzas

## Objetivo

Adaptar el contenido principal de `preview.html` al apartado `/finanzas`, reutilizando el shell autenticado definido en HU-0109 y los colores establecidos en `docs/DesignSystem-V1.md`.

Esta HU debe incorporar solamente el contenido propio del dominio Finanzas. No debe copiar ni volver a implementar:

- Sidebar.
- Header o topbar.
- Busqueda global.
- Notificaciones.
- Perfil de usuario.
- Cambio de tema global.
- Cierre de sesion.

Esos elementos pertenecen al shell y deben envolver el microfrontend mediante el `Outlet` o mecanismo de composicion vigente.

## Historia de usuario

Como usuario autenticado
quiero visualizar el espacio de Finanzas con una estructura clara para ingresos, gastos y movimientos
para comprender el alcance del modulo y disponer de una base visual consistente antes de implementar sus operaciones reales.

## Criterios de aceptacion

- [ ] `/finanzas` se renderiza dentro del shell autenticado de HU-0109 sin duplicar sidebar ni header.
- [ ] La pagina contiene breadcrumb, encabezado, descripcion y accion principal `Nuevo movimiento`.
- [ ] Existe un aviso visible que identifica el modulo como pendiente de integracion funcional.
- [ ] Se muestran cuatro cards: `Ingresos`, `Gastos`, `Saldo neto` y `Movimientos`.
- [ ] La pagina incluye las secciones `Evolucion mensual`, `Categorias de gastos`, `Movimientos recientes` y `Proximos vencimientos`.
- [ ] Se incluye un tip financiero compacto al final del contenido.
- [ ] Los colores usan tokens y clases coherentes con el Design System de Finance Ready, no variables copiadas del HTML.
- [ ] Ingresos usan success/emerald, gastos usan expense/slate y no danger/rose salvo que exista un error o atraso real.
- [ ] Saldo neto usa teal y los datos auxiliares usan colores neutrales o info cuando corresponda.
- [ ] La vista funciona en claro y oscuro aunque el mockup original este diseñado principalmente en oscuro.
- [ ] Los estados vacios no muestran `$0` como resultado financiero confirmado cuando no existen datos reales.
- [ ] Filtros, botones y acciones sin integracion no aparentan guardar, filtrar o navegar con exito.
- [ ] El contenido funciona en desktop, tablet y mobile sin scroll horizontal accidental.
- [ ] No se copia `<style>`, `<script>`, handlers inline ni manipulacion directa del DOM.
- [ ] No se agregan dependencias de graficos para representar placeholders.
- [ ] `pnpm.cmd lint` y `pnpm.cmd build` pasan.

## Decision de arquitectura

El repositorio contiene `frontend/apps/finanzas/package.json`, pero el paquete todavia no tiene scaffold ni mecanismo de composicion con el shell.

Antes de implementar, la IA ejecutora debe confirmar si HU-0109 u otro cambio ya establecio un contrato real de microfrontends.

- Si existe un mecanismo de composicion, el contenido debe vivir en `frontend/apps/finanzas/` y exportarse mediante ese contrato.
- Si no existe, la vista debe vivir temporalmente en un directorio de dominio como `frontend/apps/shell/src/finanzas/` y conectarse a `/finanzas` desde el shell.
- No se debe inventar Module Federation, iframes, un segundo router ni un segundo `ThemeProvider` dentro de esta HU.
- La ubicacion temporal debe quedar documentada como deuda arquitectonica, sin mezclar componentes de Finanzas con Dashboard.

## Decision de alcance

### Incluye

- Contenido visual del modulo Finanzas.
- Layout responsive de metricas y secciones.
- Estados vacios para graficos, categorias, movimientos y vencimientos.
- Adaptacion del modal de `Nuevo movimiento` como vista previa no persistente, solo si queda inequivocamente identificado como no disponible.
- Componentes presentacionales y tipos locales del dominio.
- Uso de componentes genericos existentes en `@finance-ready/ui-kit`.

### No incluye

- Sidebar o header propios.
- Registro real de movimientos.
- Persistencia del formulario.
- Integracion backend.
- Calculo de ingresos, gastos o saldo neto.
- Filtros funcionales por periodo.
- Graficos o distribucion real por categorias.
- Listado real de movimientos o vencimientos.
- Nuevas rutas fuera de `/finanzas`.
- Librerias externas de charts, iconos, formularios o modales.

## Modelo visual esperado

### Breadcrumb y encabezado

```text
Finanzas > Resumen

Finanzas
Registro de ingresos, gastos y movimientos personales.

[Nuevo movimiento]
```

Reglas:

- El breadcrumb debe integrarse con el espaciado del shell.
- `Nuevo movimiento` es la accion primaria teal.
- Mientras no exista persistencia, la accion debe indicar `Proximamente`, estar deshabilitada o abrir una vista previa que no permita confirmar un guardado falso.

### Aviso de estado

Mostrar un bloque info/teal que comunique:

```text
Este modulo sera implementado en una proxima iteracion.
Por ahora puedes revisar la estructura prevista para ingresos, gastos y movimientos.
```

No mostrar un toast de exito ni mensajes como `guardado visualmente`.

### Metricas

Grid previsto:

```text
Ingresos
Gastos
Saldo neto
Movimientos
```

Reglas:

- Cuatro columnas en desktop, dos en tablet y una en mobile.
- Usar `Sin datos` o `Pendiente de conectar` mientras no exista fuente real.
- No usar sparkline falsa como si representara una tendencia calculada.
- Si se conserva la zona de sparkline como placeholder, debe identificarse visualmente como no disponible.
- Ingresos: `--fr-income` / emerald.
- Gastos: `--fr-expense` / slate. Rose queda reservado para errores, atrasos o sobrepasos reales.
- Saldo neto: teal cuando sea neutral o favorable; el color futuro debe depender del valor real.
- Movimientos: neutral o info, sin introducir un azul distinto al sistema sin necesidad.

### Evolucion mensual

- Card amplia con titulo y ayuda contextual.
- Selector de periodo visible solo como disabled o informativo mientras no filtre datos reales.
- Estado vacio centrado: `Aqui veras la evolucion de tus finanzas`.
- No dibujar ejes, curvas o valores que puedan interpretarse como informacion calculada.
- No agregar una libreria de graficos hasta que exista una HU funcional con datos reales.

### Categorias de gastos

- Card complementaria con titulo y periodo.
- Estado vacio: `Aqui veras la distribucion de tus gastos`.
- El donut multicolor del mockup no debe mostrarse como distribucion real sin datos.
- Se permite un placeholder neutral accesible que no dependa solo del color.

### Movimientos recientes

- Card preparada para nombre, categoria, fecha, tipo, monto y moneda.
- En esta HU debe mostrar un estado vacio, no filas ficticias.
- `Ver todos` debe estar deshabilitado o marcado como proximo mientras no exista destino funcional.

### Proximos vencimientos

- Card preparada para obligacion, fecha, monto, moneda y estado.
- Mostrar estado vacio cuando no exista fuente real.
- Warning y danger solo se aplicaran a vencimientos o atrasos reales.
- `Ver todos` no debe navegar a una ruta inexistente.

### Tip financiero

- Card o notice compacto al final.
- Copy inicial permitido:

```text
Lleva un registro constante de tus movimientos para tomar mejores decisiones.
```

- No presentar recomendaciones personalizadas si no se basan en datos reales.
- La accion para mas tips debe estar oculta o identificada como proxima si no existe contenido adicional.

### Modal de nuevo movimiento

El mockup contiene un modal con tipo, monto, descripcion y categoria. En esta HU se permite implementarlo solo como preview del formulario futuro.

Condiciones:

- Debe anunciar claramente que aun no guarda informacion.
- No debe ejecutar `fakeSave`, mostrar exito ni alterar metricas.
- Debe poder cerrarse con boton, backdrop cuando sea apropiado y tecla `Escape`.
- Debe gestionar foco de entrada y devolverlo al trigger al cerrar.
- Los campos deben usar labels visibles y padding consistente.
- El monto no debe modelarse con `float` ni convertirse en un valor financiero dentro de esta HU.
- Si estas condiciones agregan complejidad innecesaria, preferir un boton disabled con texto `Proximamente`.

## Reglas de color y estilo

Usar `docs/DesignSystem-V1.md` y los tokens efectivos de `frontend/apps/shell/src/index.css`:

- Fondo: `background` / slate.
- Cards: `card` con borde `border`.
- Texto principal: `foreground`.
- Texto secundario: `muted-foreground`.
- Accion primaria: teal.
- Ingresos y success: emerald.
- Gastos ordinarios: slate, no rose.
- Warning: amber para compromisos proximos.
- Danger: rose solo para errores, atrasos o estados criticos.
- Info: usar el token informativo existente cuando corresponda.
- Bordes y radios moderados; sin glassmorphism ni gradientes decorativos pesados.
- Sombras minimas y consistentes con el shell.

El mockup usa gradientes, blur y colores hardcoded orientados a dark mode. Deben traducirse al sistema real, no copiarse literalmente.
