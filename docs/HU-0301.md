# HU-0301 - Integrar categorías financieras en Configuración

## Objetivo

Conectar la sección `Categorías` de `/configuracion` con los endpoints implementados en
`HU-0201`, reemplazando los fixtures visuales por categorías persistidas y pertenecientes al
usuario autenticado.

La integración debe permitir listar, crear, editar, eliminar lógicamente y restaurar
categorías de ingresos y gastos, mostrando estados de red honestos y confirmando éxito solo
después de una respuesta válida del backend.

## Historia de usuario

Como usuario autenticado
quiero administrar mis categorías financieras desde Configuración
para clasificar ingresos y gastos usando información persistida y privada de mi cuenta.

## Dependencia funcional

Esta HU depende de `HU-0201` y consume los endpoints bajo:

```text
/api/v1/transactions/categories
```

Antes de cerrar esta HU debe estar aplicada y validada en PostgreSQL la migración:

```text
e1f2a3b4c5d6_create_financial_categories_table.py
```

## Criterios de aceptación

- [ ] `/configuracion`, sección `Categorías`, carga información real del usuario autenticado.
- [ ] Los fixtures `INCOME_CATEGORIES` y `EXPENSE_CATEGORIES` dejan de mostrarse como datos.
- [ ] Existen estados diferenciados de loading, empty, error y contenido cargado.
- [ ] Las categorías activas se separan visualmente entre `income` y `expense`.
- [ ] El usuario puede crear una categoría indicando nombre, tipo y token de color.
- [ ] El usuario puede editar nombre y color, pero no el tipo.
- [ ] El usuario puede eliminar lógicamente una categoría mediante confirmación explícita.
- [ ] Las categorías eliminadas se muestran en una sección administrativa diferenciada.
- [ ] El usuario puede restaurar una categoría eliminada y conservar su ID.
- [ ] La UI consume paginación por cursor sin duplicar registros.
- [ ] `401` cierra la sesión y conduce al flujo de login existente.
- [ ] `403`, `404`, `409`, `422` y errores de red muestran mensajes accionables.
- [ ] Un conflicto `category_name_conflict` se presenta junto al campo nombre.
- [ ] Ningún mensaje de éxito aparece antes de la confirmación del backend.
- [ ] Los tokens de color se traducen mediante un mapa estático de clases, no interpolación
  dinámica de Tailwind.
- [ ] Los contratos frontend coinciden con los schemas backend y no exponen `user_id`.
- [ ] La vista funciona en claro, oscuro, desktop y mobile.
- [ ] Backend Ruff/Pytest y frontend lint/build pasan.

## Decisión de arquitectura

- Mantener la implementación dentro de la app funcional
  `frontend/apps/shell`; no crear un microfrontend nuevo.
- Crear el cliente del dominio en:

```text
frontend/apps/shell/src/transactions/categoriesApi.ts
```

- Mantener la composición de la experiencia en:

```text
frontend/apps/shell/src/configuracion/
```

- Extraer el panel a `FinancialCategoriesPanel.tsx` si evita seguir aumentando
  `ConfiguracionPage.tsx`.
- Colocar los contratos estables de API en
  `frontend/packages/shared-types/src/index.ts`.
- No agregar React Query, Zustand, Redux, librerías de formularios ni dependencias de modal.
- El backend continúa siendo la fuente de verdad para ownership, normalización, unicidad y
  eliminación lógica.

## Decisión de alcance

### Incluye

- Contratos TypeScript de categorías.
- Cliente HTTP autenticado para categorías.
- Listado y paginación mediante cursor.
- Filtro visual por categorías activas y eliminadas.
- Crear, editar, eliminar y restaurar.
- Mapeo de tokens de color.
- Estados loading, empty, error y submitting.
- Confirmación de eliminación.
- Mensajes accesibles de resultado.
- Validación backend, frontend y manual.

### No incluye

- Movimientos financieros.
- Categorías predeterminadas o sugeridas.
- Subcategorías, iconos, presupuestos o estadísticas de uso.
- Cambio de tipo después de crear una categoría.
- Eliminación física.
- Reasignación de movimientos asociados.
- Preferencias financieras, perfil, contraseña, sesiones, umbrales o eliminación de cuenta.
- Cambios al contrato backend aprobado en `HU-0201`.
- Cambio de `Money.amount`; esta integración no transporta dinero.
- Scaffold de `frontend/apps/configuracion` o `frontend/apps/finanzas`.

## Contratos TypeScript

Agregar en:

```text
frontend/packages/shared-types/src/index.ts
```

Contratos equivalentes a:

```ts
export type FinancialCategoryType = 'income' | 'expense';

export type FinancialCategoryColorToken =
  | 'slate'
  | 'sky'
  | 'teal'
  | 'violet'
  | 'fuchsia'
  | 'cyan'
  | 'orange'
  | 'pink'
  | 'emerald'
  | 'amber'
  | 'indigo'
  | 'rose';

export type FinancialCategory = {
  id: number;
  name: string;
  type: FinancialCategoryType;
  color_token: FinancialCategoryColorToken;
  created_at: string;
  updated_at: string;
  deleted_at: string | null;
};

export type FinancialCategoryCreateRequest = {
  name: string;
  type: FinancialCategoryType;
  color_token: FinancialCategoryColorToken;
};

export type FinancialCategoryUpdateRequest = {
  name?: string;
  color_token?: FinancialCategoryColorToken;
};

export type FinancialCategoryListResponse = {
  items: FinancialCategory[];
  next_cursor: string | null;
  has_more: boolean;
};

export type DomainErrorDetail = {
  code: string;
  message: string;
  field: string | null;
};
```

Reglas:

- No incluir `user_id` en contratos públicos.
- No usar `any`.
- No reutilizar tipos de fixtures visuales como contrato API.
- `type` no pertenece a `FinancialCategoryUpdateRequest`.
- Los timestamps se transportan como strings ISO; el frontend no los reinterpreta como
  fechas financieras.

## Contrato del cliente API

Crear:

```text
frontend/apps/shell/src/transactions/categoriesApi.ts
```

Exponer funciones equivalentes a:

```text
listFinancialCategories
createFinancialCategory
updateFinancialCategory
deleteFinancialCategory
restoreFinancialCategory
```

Cada función:

- recibe `token` explícitamente;
- usa `appConfig.apiUrl`;
- envía `Authorization: Bearer <token>`;
- agrega `Content-Type: application/json` solo cuando existe body JSON;
- codifica query params con `URLSearchParams`;
- parsea errores de dominio sin asumir que toda respuesta fallida contiene JSON válido;
- distingue status HTTP, código de dominio y error de red;
- no accede directamente a `localStorage`.

Crear una clase o estructura de error pequeña y local, por ejemplo:

```ts
type CategoriesApiError = {
  status: number | null;
  code: string;
  message: string;
  field: string | null;
};
```

No crear todavía una abstracción HTTP global. Promover un cliente compartido únicamente
cuando exista un segundo dominio consumidor y un contrato común demostrado.

## Estados de interfaz

El panel debe manejar explícitamente:

```text
initial/loading
loaded
empty
load_error
submitting
mutation_error
success
```

Reglas:

- Loading inicial no muestra fixtures ni estados vacíos prematuros.
- Empty diferencia ausencia de categorías activas y ausencia de eliminadas.
- Load error conserva una acción `Reintentar`.
- Durante una mutación, deshabilitar solamente controles que puedan duplicarla.
- Los mensajes se anuncian con una región `aria-live` apropiada.
- Un mensaje success se establece después de recibir `2xx` y actualizar o recargar el estado.
- Al recibir `401`, ejecutar `logout()` del contexto existente; `ProtectedRoute` gestiona la
  navegación al login.
- `403` informa que la cuenta no está habilitada para la operación.
- `409 category_name_conflict` marca el campo `name` y conserva los datos del formulario.
- `422 invalid_cursor` reinicia la colección y permite reintentar desde la primera página sin
  reutilizar el cursor inválido.
- Otros `422` muestran un error de validación sin inventar el detalle de Pydantic.

## Paginación

La carga inicial usa:

```text
GET /api/v1/transactions/categories?include_deleted=true&limit=50
```

Reglas:

- Mantener `next_cursor` y `has_more` de la respuesta.
- `Cargar más` solicita la siguiente página con el mismo `include_deleted` y límite.
- Concatenar por ID sin duplicados.
- No interpretar, modificar ni persistir el cursor en `localStorage`.
- Un cambio de sesión reinicia items y cursor.
- Separar en memoria categorías activas y eliminadas únicamente después de recibirlas; el
  backend continúa siendo la fuente del estado `deleted_at`.

## Tokens de color

Definir un mapa exhaustivo y estático, por ejemplo dentro del componente de categorías:

```ts
const CATEGORY_COLOR_CLASSES: Record<FinancialCategoryColorToken, string> = {
  slate: 'bg-slate-400',
  sky: 'bg-sky-400',
  teal: 'bg-teal-400',
  violet: 'bg-violet-400',
  fuchsia: 'bg-fuchsia-400',
  cyan: 'bg-cyan-400',
  orange: 'bg-orange-400',
  pink: 'bg-pink-400',
  emerald: 'bg-emerald-400',
  amber: 'bg-amber-400',
  indigo: 'bg-indigo-400',
  rose: 'bg-rose-400',
};
```

No usar:

```ts
`bg-${color}-400`
```

El indicador debe incluir nombre o texto de tipo; el color no puede ser la única fuente de
información.

## Crear y editar

Usar un formulario accesible con:

```text
Nombre
Tipo
Color
```

Reglas:

- En creación, `type` es obligatorio y permite `income` o `expense`.
- En edición, mostrar el tipo como solo lectura y no enviarlo al backend.
- Nombre obligatorio, máximo visual de 80 caracteres y validación final en backend.
- Color obligatorio mediante opciones de la lista aprobada.
- Asociar labels y controles.
- Gestionar foco inicial, `Escape`, cierre explícito y retorno al trigger si se usa modal.
- No cerrar el formulario ante error de red, `409` o `422`.
- Al confirmar éxito, incorporar la respuesta del backend o recargar la primera página.

## Eliminar y restaurar

- Eliminar requiere confirmación que explique que la categoría se puede restaurar.
- No eliminar una fila del estado antes de recibir `204`.
- Después de eliminar, moverla a eliminadas mediante recarga o estado confirmado.
- La sección `Categorías eliminadas` debe diferenciar visualmente registros inactivos.
- Restaurar llama `POST /{id}/restore` y espera `200`.
- No afirmar que se restauró hasta recibir la categoría activa del backend.
- Un `404` durante mutación informa que el recurso ya no está disponible y recarga la lista.

## Riesgo residual

- Las categorías todavía no clasifican movimientos porque el CRUD de movimientos no existe.
- No existen categorías iniciales; un usuario nuevo verá un estado vacío legítimo.
- El frontend no dispone actualmente de una suite de tests de componentes configurada; esta
  HU exige lint, build y validación manual, y deja la estrategia de tests frontend como una
  decisión separada.
- Las categorías eliminadas no tienen movimientos asociados todavía. La conservación de
  referencias históricas deberá validarse cuando se implemente el modelo de movimientos.
- Cambiar `Money.amount` de `number` a string continúa pendiente, pero no afecta esta HU.
